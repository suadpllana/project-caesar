`/app/rt/prio.py` is rewritten. Nothing else in the tree was changed (my scratch scenarios and checker were deleted).

**The policy.** A task's effective priority is defined as a pure function of the core's current state: the max of its own base priority and the base priorities of every task that is waiting on a mutex it holds, following the chain transitively (waiters on mutexes held by those waiters, and so on). All four hooks — `blocked`, `granted`, `released`, `expired` — recompute that value for every task and write it via `core.set`. Those four are the only points where "who holds what" or "who waits on what" can change, so the value is exactly correct at every tick boundary, in both directions: no lift without an accountable waiter, no lift left behind once the last waiter is gone.

The transitive walk carries a `seen` set, so a deadlock cycle (A waits on B's mutex while B waits on A's) terminates instead of recursing forever.

**Why the old code failed.** `released` reset the holder to its base priority unconditionally, ignoring any other mutex it still held. On your run, task 4 released mutex 1 at tick 10 and dropped 9→1 while task 2 was still queued on mutex 2, which task 4 still held. With the rewrite it drops 9→5 (task 2's priority), keeps the processor, and:

| | old | new |
|---|---|---|
| task 2 granted mutex 2 | tick 29 | tick 17 |
| task 2 finishes | tick 33 | tick 21 |
| task 3 (priority 4) runs 14–25 ahead of task 2 | yes | no |

The first two changes you identified as correct, `[5, 4, 5]` at tick 5 and `[7, 4, 9]` at tick 7, are unchanged.
