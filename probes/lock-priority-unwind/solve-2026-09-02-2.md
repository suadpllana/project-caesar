## What was wrong

`released` reset the holder to its base priority unconditionally. Releasing *one* mutex dropped the lift even though a waiter was still queued on a *different* mutex the task held — which is exactly the tick-10 collapse: task 4 released mutex 1, fell to 1, and task 3 (priority 4) ran 14–25 while task 2 (priority 5) sat on mutex 2. `granted` and `expired` did nothing, so a lift also outlived the waiter that caused it, and `blocked` propagated only one hop, using `eff` rather than a transitive maximum.

## What I did

Rather than patch each event, `sync()` recomputes every task's effective priority from the core's live state on all four events. The value is a pure function of (who holds what, who is queued on what, bases), so:

- **`blocked`** — the new waiter's base propagates up the whole holder chain, however deep.
- **`granted`** — the granted task leaves the queue, so its contribution disappears from the previous holder immediately.
- **`released`** — the holder keeps whatever the waiters on its *other* mutexes justify, and drops only when nothing is behind it.
- **`expired`** — the timed-out waiter is gone from the queue, so its lift evaporates; the mutex, holder and remaining queue are untouched.

It's idempotent and symmetric, so it can't over-lift or leave a stale lift. Deadlock cycles are broken with an in-progress set (each cycle member still ends up with the max base over the cycle).
