The tree under `/app` is the filing end of our evaluation harness, cut down small enough to argue about. Runs post scores for items. A matcher keeps telling us that two of the keys we score under are the same item, and a board has to be handed one line per key it watches. A report set is a text file of the runs, the matchers, the keys the board watches and a script of what each source does; `/app/sets` holds three, and `/app/run_bind.py` takes one and prints what happened, a row to a line.

Run it on `/app/sets/plain.txt`. Key 2 is filed on the second tick at `["fl", 2, 2, 2, 40]`, and the third tick comes back empty: `m0` had a sameness to declare about keys 2 and 9, and by then there was nothing left of key 2 to name. The 40 on that line is `r1`'s score. Key 9 was already carrying `r0`'s 17 when the line was written, and `r0` comes before `r1`. That row went too early.

Here is the machine underneath. Keys are integers and start out one item apiece. A run has a pool of keys and may post a score for any key in its pool it has not posted for yet; a tag has a pool and may say that two keys in its pool are one item, or that two of them are not; both shut, and after that they do nothing. The board watches some of the keys, and each watched key earns exactly one line, which reads: the key we were asked about, then the smallest key in the item that key now belongs to, then the score of the first post that item carries, first meaning by the name of the run that posted it and, within the one run, by the key it was posted for; an item that no run has posted for yet has no line to write and waits until one arrives. A line handed to the board takes its item off the desk, and the tags work from what is on the desk, so a sameness or a difference naming a key that has gone is not an event and nothing whatever comes of it; the runs know nothing about the board and go on posting. Two watched keys can share an item. Each still earns its own line. When several watched keys come ready on one tick their lines go in order of the key asked about. Every event is a row. A post, a sameness, a difference, a shut, a filing, and the tick the set ended on.

The filing decision is the one we rewrote last quarter. It has been wrong since.

What we need back is this: a watched key is filed at the first tick at which nothing that could still happen would change the line it would carry, and not before. We grade both halves. Filing a line that a later sameness or a later post moves is wrong, and that is what produced the row above. Holding a line back once nothing that could still happen would move it is wrong in the same measure, so a submission that waits for every source to shut fails as hard as one that files on sight. Judge from what is known when the question is put, never from what the set goes on to do.

So the shape of the input matters. A run that has not shut may post a score for any key of its pool it has not posted for, whenever it likes and in whatever order suits it, and once shut it posts nothing at all; a tag that has not shut may say that any two keys of its pool are one item, as often as it pleases, and it may say instead that any two of them are not, and once shut it says nothing further. Nothing ever declares two keys the same when something already stands saying they differ. Nothing ever declares two keys different when something already stands saying they are the same. Every key the board watches is posted for at least once before the set ends, and every run and every tag is shut before the set ends.

The sets we grade are no straight lines, and five of their shapes are worth naming, since a rule fitted to a straight line survives none of them. Tag pools overlap, so a key can arrive in an item by way of a key that neither the board nor the run that scored the item ever mentioned, and the tags carrying it there can be several. Differences get declared between keys sitting in items of their own, and between keys that later end up in items holding several keys apiece. Several runs stand open at once over pools that overlap, so the score a line would carry is not settled by whichever post landed first, and a matcher can go on working long after the run that scored an item has shut, on keys that run never touched. The board watches several keys whose items one tag can reach, and a tick often owes it more than one line.

Four behaviours must survive, and we grade those as hard as the rest. A tag that has shut welds nothing more, so it holds no key back, and a tag whose pool lies wholly inside one item alters nothing whatever. An item already holding the smallest key any open tag could bring it, with no open run able to get in ahead of the post it carries, is filed at once. And a set with no difference in it anywhere is filed by the same rule as every other, with nothing special done for it.
