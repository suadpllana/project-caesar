The tree under `/app` is the filing end of our evaluation harness. Runs post scores for items, tags tell us when two of the keys we score under are the same item, and every key we watch has to come back with exactly one row. A report set is a text file naming the runs, the tags, the keys watched and a script of what each source does; `/app/sets` holds three, and `/app/run_bind.py` takes one and prints what happened, a row to a line.

Run it on `/app/sets/plain.txt`. Key 2 is filed on the second tick at `["fl", 2, 2, 2, 40]`, and the third tick comes back empty: `m0` had a tie to declare between keys 2 and 9, and by then key 2 was gone. The 40 is `r1`'s score. Key 9 was already carrying `r0`'s 17 when that row was written, and `r0` comes before `r1`. It went too early.

Here is the machine. Keys are integers and start out one item apiece. A run has a pool of keys and may post a score for any key in its pool it has not posted for yet; a tag has a pool and may tie two keys in it, meaning they are one item, or bar two of them, meaning they are not; both shut, and after that they do nothing. Each watched key earns exactly one row, which reads: the key asked about, then the smallest key in the item that key now belongs to, then the score of the first post that item carries, where first means by the name of the run that posted it and, within one run, by the key it was posted for; an item no run has posted for has no row to write and waits until a post arrives. Filing a row takes its item out of the machine. A tag is handed its pool once, so the moment any key of that pool is filed the pool is stale and the tag says nothing further; a tie or a bar from a tag that has stopped, or naming a key that has gone, is not an event and nothing comes of it. The runs are unaffected and go on posting. Two watched keys can share an item. Each still earns its own row. When several come ready on one tick their rows go in order of the key asked about. Every event is a row. A post, a tie, a bar, a shut, a filing, and the tick the set ended on.

We rewrote the filing decision, and it has been wrong since.

What we need back is this: a watched key is filed at the first tick at which nothing that could still happen would change the row it would carry, and not before. We grade both halves. Filing a row that a later tie or a later post moves is wrong, and that is what produced the row above. Holding one back once nothing that could still happen would move it is wrong in the same measure, so a submission that waits for every source to shut fails as hard as one that files on sight. Judge from what is known when the question is put, never from what the set goes on to do.

So the shape of the input matters. An open run may post for any key of its pool it has not posted for, whenever it likes and in whatever order suits it, and once shut it posts nothing at all; an open tag may tie any two keys of its pool as often as it pleases, or bar any two of them instead, and once shut it says nothing further. Nothing ever ties two keys that something already bars. Nothing ever bars two keys that something already ties. Every watched key is posted for at least once before the set ends, and every run and every tag shuts before the set ends.

The sets we grade are not straight lines. Tag pools overlap, so a key can arrive in an item by way of a key that neither the watch list nor the run that scored the item ever mentions, and the tags carrying it there can be several. Bars are declared between keys sitting alone and between keys that later end up in items holding several apiece; several runs stand open at once over pools that overlap, and a tag can go on working long after the run that scored an item has shut, on keys that run never touched. More than one watched key is commonly reachable by one tag, and a tick often owes more than one row.

Four behaviours must survive, and we grade those as hard as the rest. A tag that has shut ties nothing more, so it holds no key back, and a tag whose pool lies wholly inside one item alters nothing; an item already holding the smallest key any open tag could bring it, with no open run able to get in ahead of the post it carries, is filed at once. And a set with no bar in it anywhere is filed by the same rule as every other. Some graded no-bar sets have tag pools containing 25 to 30 keys. The verifier allows 600 seconds for the complete run; a submission that does not finish within that limit scores 0.
