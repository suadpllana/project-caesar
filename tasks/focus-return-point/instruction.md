The focus controller of our terminal toolkit has been wrong since we rewrote it, and every bug report says the same thing: the cursor jumps to the top of the form. `/app/ui` is the toolkit. `/app/ui/core.py` holds the widget tree and the screen stack and applies every event; `/app/ui/focus.py`, `/app/ui/keep.py`, `/app/ui/reach.py` and `/app/ui/mem.py` decide where focus goes, and those four are the files you may change. `/app/run_ui.py` takes a script and prints one line per event: the event, then the widget holding focus afterwards, or `none`.

Run `/app/run_ui.py` on `/app/cases/dialog.txt`. The user is on `f3`, a button inside a row of the form, when the confirmation screen `ask` goes up; the row is removed while that screen is showing; then the screen is popped. The last four lines of the printout are `4 push ask -> a1`, `5 drop box -> a1`, `6 pop ask -> f1` and `7 tab -> f2`. Focus has gone back to the first field of the form and the next Tab has landed on the second, as if the user had never been anywhere. The row stood between `f2` and `f5`. That is where the next Tab has to pick up from. `/app/cases/stacked.txt` is a second script. Both are ordinary.

A script declares screens with `screen` lines and widgets with `w` lines, id then parent then flags, children in declaration order. `foc` marks a widget that can hold focus. `hid`, `off` and `shut` are the three ways a widget starts out unavailable; `hide`/`show`, `off`/`on` and `shut`/`open` set and clear them. `comp` marks a composite. `grp=<name>` puts a widget in a group and `sel` marks the selected member; `pick` selects a member. `auto` marks where a screen would like to start. The remaining events are `push` and `pop` with a screen name, the keys `tab`, `back`, `next` and `prev`, `want` with a widget id, `drop` with a widget id, `add` with a new id, a parent, an index and flags, and `move` with a widget id, a parent and an index. Every event prints one line. Every line is graded.

Some rules, and several of them are not what a browser does.

A widget can take focus while it is in the tree, on the screen on top, carries `foc`, and neither it nor any container above it is hidden, disabled or shut. Composites may nest. The screen and each composite have their own list of stops in tree order. A nested composite is one stop in the nearest surrounding composite, or in the screen if there is none; its descendants are not separate stops in that list. It is a stop only while something inside it can take focus. Other focusable widgets belong to their nearest surrounding composite, or to the screen. Within each list, a group contributes its selected member when that member can take focus, otherwise its first member that can. Each group name has at most one selected member on a screen at any time. A `pick` clears selection on all same-named members on the screen, including those in other composites, before selecting its target. Composites themselves carry neither `foc` nor `grp`.

The `tab` and `back` keys use the screen's list, wrapping at its ends. From any widget or place inside a composite, they leave the outermost composite. The `next` and `prev` keys start with the innermost composite containing the focused widget. They seek the next or previous stop after that widget's position, including when a `want` put it on an unselected group member. At the end of that list they continue in the enclosing composite, from the child composite's position, and repeat until they find a stop or run out of enclosing composites. They never enter the screen's list and never wrap. Outside a composite, or with nothing holding focus, they do nothing.

Each composite remembers the last direct stop through which focus landed inside it: the child composite on that path, or the focused widget if no child composite is on the path. Every landing updates all enclosing composites, including a landing by request or screen return. Entering a composite by any key follows that remembered stop if it still belongs to that list's scope and can lead to focus, even if a remembered widget is now an unselected group member. Otherwise it takes the first current stop in that list. A child composite is entered by the same rule, so a remembered branch whose former focused widget is unavailable may still lead to another widget in that branch. Moves and selection changes do not rewrite memories; their validity is checked on entry. The screen on top is the whole world. No key reaches a screen underneath it.

A `want` for a widget on the screen on top gives it focus if it can take focus. Otherwise it does nothing at all. A `want` for a widget on any other screen that still exists is kept, the latest per screen, and answered when that screen next comes on top, by a `push` or by the screen above it going away: the widget takes focus if it can at that moment; if it cannot, nothing holds focus and the next key starts from that widget's place. A `push` with nothing kept lands on the first widget in tree order carrying `auto` that can take focus, else on the first stop, else nothing holds focus and the next `tab` starts at the top of that screen.

When the screen on top is popped and nothing is kept for the one underneath, focus goes back to the widget that had it there when the popped screen went up, provided it can take focus at that moment. If it exists and cannot, nothing holds focus and the next key starts from its place. If it has been dropped, the next key starts from where it stood. If nothing held focus when the popped screen went up, nothing holds it after the return and the next key starts from the place it would have started from then. A screen may be popped while others stand above it. It takes nothing with it, and when the screen above it is popped in turn, that screen returns to wherever the lower one would have returned to. Popping the last screen leaves nothing holding focus and nothing for the keys to do. No screen is pushed twice. A pop is final.

Losing focus is never a jump to the top. When the widget holding focus is hidden, disabled, shut, dropped or moved somewhere it cannot take focus, or a container above it is, nothing holds focus; the next `tab` goes to the first stop after that widget's place, `back` to the last stop before it. For a widget still in the tree the place is the widget itself, wherever it is now. For a dropped widget the place is the container it was in and the position it had among that container's children, and it does not shift when siblings are added or removed: a widget added at that position stands at the place and is the first thing a `tab` reaches. If the container itself is dropped, the place is where the container stood, and so on upward. A widget shown or enabled again does not take focus back by itself. A `pick` moves the selection. Focus stays put.

An `add` may reuse an id after its old widget has been dropped. Saved return targets, kept requests, places and composite memories refer to widget instances: the replacement does not inherit them, and an old target stays tied to its old place. Later events naming that id address the replacement.

Rendering can group edits with `begin`, `commit` and `abort`, each without arguments. A `begin` opens a render transaction; transactions nest up to four deep and close in reverse order. All declarations precede events, every transaction is closed, and no `push` or `pop` occurs inside one. Tree edits take effect immediately. While any transaction remains open, every printed line retains the focus reported at the outermost `begin`, even when that widget has been dropped or made unavailable. The ordinary immediate focus rules resume when the outermost transaction closes.

Inside a transaction, keys and `want` wait in their original order. A `want` binds the widget instance named when it is issued; an id absent then is ignored, even if it appears later. An inner `commit` keeps its edits and waiting actions inside the outer transaction without answering them. An `abort` undoes everything since its matching `begin`, including inner commits: original widget instances, flags, selection, parents and child order return; new widgets disappear; waiting actions and removal positions from those abandoned edits are discarded. An id freed by an abort can be used again. The focus position, composite memories and previously kept requests survive an abort unchanged.

The outermost `commit` first checks the retained focus against the final tree. If it cannot remain, focus is lost by the place rules above. It then answers all waiting keys and requests in order against that same final tree, without replaying the edits. Their landings update composite memories normally. A bound request whose widget was dropped does nothing on the top screen; for another surviving screen it becomes the kept request for that retired instance, so its old place still matters when that screen comes on top. Hiding then showing a focused widget within one committed render therefore does not lose focus; hiding it in one committed render and showing it in another does.

Widgets are dropped, hidden, disabled, then enabled again while they hold focus and while a screen above them is up; requests arrive for screens that are not on top, including screens not yet pushed; screens are popped out of order; and render transactions commit or abandon edits. The scripts we grade do all of that over as many as five screens, with at most forty widget creations in total, counting the initial declarations and every `add`, including creations later abandoned. None of it is rare.

We grade the printed focus after every event of every script, exactly, on the scripts in the tree and on scripts you have not seen. Nothing outside the four files is read. `/app/ui/core.py` and the rest stay as they are.
