The debugger in `/app` is the one we use on programs for our small stack machine. It stops in the wrong places, most of them around code the compiler inlined. It is also slow. It moves the program one instruction at a time, so a session that crosses a long loop takes far longer than anyone can wait. Running `python3 /app/run_dbg.py IMAGE SCRIPT TAPE` plays a session. It prints one line per command. There are four sessions in `/app/samples`. The one called `long` is as heavy as the heaviest one we grade. The first six commands of `/app/samples/calls` are `break 17`, `break 2`, `break 8`, `run`, `step` and `step`, and they must print `b1 18`, `b2 0`, `b3 11`, `hit 0 main:2`, `hit 18 f0:17 main:2` and `step 21 f0:18 main:2`.

The program runs in a separate target process. The debugger reaches it only through `/app/tgt/link.py`, where `pc()` gives the program counter, `stack()` the return addresses of the active calls, outermost first, `step()` executes one instruction, and `go(stops)` executes at least one instruction and carries on until the program counter is in `stops` or the program ends, and each of those is a round trip between the two processes. The tape the program reads belongs to the target. When we grade, each session runs in a fresh process as an unprivileged user, in a copy of `/app` it cannot write, and the debugger has no way to read the tape. You may change `/app/dbg/marks.py`, `/app/dbg/frames.py` and `/app/dbg/steps.py`. Only those three files are collected. They must keep `resolve`, `show` and `Engine`, with its `hid` and its `run`, `cont`, `step`, `next` and `finish`, as `/app/dbg/sess.py` uses them. Everything else stays as it is.

An image starts with its functions, `fn NAME LO HI` or `fn NAME LO HI L1 L2`, in address order from 0 with no gaps. Addresses LO to HI belong to the function. Lines L1 to L2 are its source lines. No line belongs to two functions. The program starts at address 0. It ends when a `ret` has no call to return to. Each address holds one instruction, written `ADDRESS OP ARGS`, which is one of `nop`, `set R K`, `in R` (the next number on the tape), `dec R`, `jnz R A` (jump to A if R is not 0), `jmp A`, `call A` (A is the first address of a function) or `ret`. Registers `a` to `d` belong to each call. They start at 0.

The entry `row A L` starts a row at A for line L. A trailing `x` marks a row that is not a statement. Line 0 is code with no line. No two rows share an address. A row covers the addresses up to the next row of its function or the end of the function. A function declared without lines has no rows. One declared with lines starts with a statement row whose line is not 0. The entry `inl ID F P C LO HI` says addresses LO to HI hold the body of function F inlined into P, a function or an earlier instance, from line C of P, its call line. An instance lies inside its parent and never overlaps a sibling. Execution enters an instance only at LO from outside it and leaves only by running from HI to HI+1. An instance holds no `ret`. Its first address LO starts a statement row whose line is not 0. Address HI+1 starts a row. Every row carries a line of the innermost function or instance holding its address, or 0.

A script holds one command per line. Every command prints one line. The command `break L` numbers breakpoints from 1 and prints `bN` followed by its addresses in ascending order. A statement row belongs to the innermost function body or instance holding its address, and each body or instance with statement rows of line L gives the breakpoint one address, the lowest of them. Every `break` names a line that has a statement row. The command `run` starts the program. It comes once, before any `cont`, `step`, `next` or `finish`. When the program ends, the command prints `exit` and no command follows. Any other stop prints its kind, the program counter and the frames innermost first, each as `NAME:LINE`. The kind is `hit` at a breakpoint, `step` at the end of a `step` or `next`, and `done` at the end of a `finish`.

The innermost frame is read at the program counter and each caller at its return address minus one, its `call`, and at that address the scopes of a frame are its function and then every instance holding the address, outermost first. An instance prints the name of the function it inlines. A scope shows the call line of the scope below it, and the deepest shows the line of the row holding the address, or 0. The innermost frame may have its deepest scopes hidden. Hidden scopes are not printed. The scope above them still shows the call line of the first hidden one. Each stop decides what is hidden until the next. A stop hides nothing unless a rule below says so.

A hit happens whenever execution arrives at a breakpoint address, in any frame. It ends the command there. The instruction a command starts at runs without that check, except that `run` stops at once when address 0 is a breakpoint. The command `cont` runs until a hit or the end.

Both `step` and `next` step the innermost frame. Its deepest visible scope is the stepping scope. The line that scope shows is the stepping line. If scopes are hidden, `step` makes the outermost hidden one visible and stops without running anything, and `next` runs until the frame leaves that instance and then judges where it lands. Otherwise they run, and:

- A call made by the stepping frame: `next` runs it until it returns, and `step` stops at the first address of the called function if that function has lines, hiding the instances that start there, and otherwise runs it until it returns. A call that returns counts as a move from the `call` to its return address.
- When the stepping frame returns, its caller becomes the stepping frame. The innermost scope of the caller at the return address, not counting instances that start exactly there, becomes the stepping scope. The stepping line is kept and the arrival is judged.
- Execution arriving in a different row of the stepping frame is judged. If it has left the stepping scope, the enclosing scope that holds the new address becomes the stepping scope first. If the address is the first of instances below the stepping scope, the outermost of them decides: when its call line equals the stepping line, `step` stops with it visible and the deeper ones hidden, and `next` runs until the frame leaves it and then judges where it lands; when it does not, both stop there with all of them hidden. Otherwise the position in the row decides. At the first address of a row, a statement row whose line is not 0 and differs from the stepping line stops the command. Part-way into a row, a line that is not 0 becomes the stepping line. No other arrival stops them or changes the stepping line.

When the deepest visible scope of the innermost frame is an instance, `finish` runs until the frame leaves that instance. Otherwise it runs until the innermost frame returns. It stops where it lands, hiding the instances that start there. No script issues `finish` in the outermost frame while its deepest visible scope is its function.
