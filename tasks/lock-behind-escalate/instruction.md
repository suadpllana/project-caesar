`/app` is the lock manager of an embedded transactional store, cut down to the part that decides which transaction holds which lock. A script file names a set of transactions and gives each one its ops in order. `cfg K` opens the file and sets the escalation threshold. Every other line is `T<n> lock <target> <mode>`, `T<n> drop <target>` or `T<n> commit`, where a target is a table, written as a name with no dot, or a row of one, written `<table>.<n>`, and a mode is `s` or `x`. The ops of a transaction are its lines in file order, and its last line is `commit`. Transactions are ordered by their first line. `/app/run_lm.py` takes a script and prints a line for each thing that happens. `/app/scripts` holds four scripts.

The driver is fixed and runs the transactions in rounds. In a round the transactions are visited in order, and one that has neither committed nor been killed, is not waiting for a lock and has an op left performs its next op, after which the manager settles. A transaction granted a lock during a settle acts at its next visit. The program ends when every transaction is done.

We rewrote the manager last cycle and it has been wrong since. Run `/app/run_lm.py` on `/app/scripts/small.txt`. The third line comes out `grant T3 t.1 s` and should be `wait T3 t.1 s`: T2 asked for that row in `x` before T3 did.

The files you may change are `/app/lm/held.py`, `/app/lm/wait.py`, `/app/lm/grant.py`, `/app/lm/esc.py`, `/app/lm/dead.py` and `/app/lm/settle.py`. Nothing else. The rest of the tree is replaced by our own copy before a script is run, a new file put beside those six included.

A transaction holds records. A record is one target in one mode, and a transaction holds at most one record per target. Two locks conflict when their targets overlap, they belong to different transactions, and they are not both `s`; a target overlaps itself, and a table overlaps every row of it. Every `lock` op takes the next sequence number, so an earlier request is one made by an earlier `lock` op. A request is granted only when no record held by another transaction conflicts with it and it is not behind any earlier waiting request it conflicts with; otherwise it waits. It is not behind such a waiter when the transaction that made the earlier request is waiting, directly or through other waits, on the requester. A waiting transaction waits on another when its request conflicts with a record the other holds, or with an earlier waiting request of the other.

After every op the manager settles. While some waiting request is grantable, the earliest of them is granted. When none is, and there are transactions each waiting on a record the next one holds, around a cycle, the one holding the fewest records among all transactions on such cycles is killed, a tie going to the one whose waiting request is the most recent. This goes on until nothing changes. A killed transaction prints `dead` with its number of records, releases them all, drops its request and is done. The rest of its lines are never run.

A request for a target the transaction already holds in the requested mode or in `x`, or for a row of a table it holds in the requested mode or in `x`, is granted at once and records nothing. Asking for `x` on a target held in `s` is an ordinary request, and when it is granted the record's mode becomes `x`. Once a table lock is granted, the row records the transaction holds on that table in the same mode or a weaker one are released.

After any grant of a row of table A to a transaction, including one that recorded nothing, if the transaction holds K or more row records on A it tries for A, in `x` if any of those records is `x` and in `s` otherwise, unless it already holds A in that mode or in `x`. The try is a request judged as if it had been made after every request that is waiting. When it is grantable it is taken at once, as a table grant, and prints `esc`. Otherwise it is given up, and tried again only at its next row grant on A. It never waits. It takes no sequence number.

`drop` releases the record the transaction holds on exactly that target, and does nothing when there is none. `commit` releases every record the transaction holds.

`grant T target mode` is printed when a request is granted, at once or later, `wait T target mode` when it first has to wait, `esc T table mode` when an escalation is taken, `end T n` when T commits and `dead T n` when it is killed, where n is the number of records released. Nothing else is printed. Within one op, the line for the op itself comes first and then the lines the settle produced, in the order it produced them, and an `esc` line follows the grant that brought it on.
