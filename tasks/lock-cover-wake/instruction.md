`/app` is the lock table of a storage engine. What is left of it is the part that decides who holds what and who runs next. A script is one run of a workload: `cfg E` sets the row limit used below, `beg t` begins transaction t, `req t <resource> <mode>` asks for a lock and `com t` commits. A resource is a table, written as a number, or a row of one, written `<table>.<row>`. A table is locked in IS, IX, S, SIX or X. A row takes S or X. `/app/run_lk.py` takes a script and prints a line for each thing that happens. `/app/plans` holds four scripts. One transaction is older than another when it began first; the numbers they are given say nothing about that.

We rewrote this half last cycle. It has been wrong since. Run `/app/run_lk.py` on `/app/plans/tiny.txt`. The line for transaction 41 comes out `tx 41 run`, and it should read `tx 41 wait`.

The files you may change are `/app/lk/mode.py`, `/app/lk/ent.py`, `/app/lk/txn.py`, `/app/lk/ask.py`, `/app/lk/wake.py`, `/app/lk/lift.py` and `/app/lk/tell.py`. Nothing else. The rest of the tree is replaced by our own copy before a script is run, a new file put beside those seven included. `/app/run_lk.py` builds `lk.ask.Engine` on the list the lines go into, calls its `step` once for each command in order, and then extends that list with `lk.tell.report` of the engine.

One mode covers another when holding the first is already enough for the second. IS is the weakest. IX and S each cover IS and cover nothing of each other; SIX covers IS, IX and S; X covers every mode. The cover of two modes is the weakest mode covering both, so IX with S is SIX. Two modes held on one resource by different transactions conflict unless one of them is IS and the other is anything but X, or both are IX, or both are S. A request for a mode the transaction already covers takes no lock and prints nothing. It is covered by the lock that transaction holds on the resource asked for, or, for a row, by the lock it holds on that row's table. Requests satisfied this way are counted. The count is reported at the end.

A row in S needs IS on its table and a row in X needs IX. That table request is made first, and when it cannot be granted at once the row request goes into the queue with it and is made at the moment the table request is granted, against the lock table as it stands then.

A request by a transaction that already holds the resource is a conversion, to the cover of the mode it holds there and the mode it asks for. It is tested against what the other transactions hold, never against its own. Every other request is a new one. A new request is granted at once when nothing is queued on that resource and no other transaction holds a mode conflicting with it. A conversion is granted at once when no conversion is queued on that resource and no other transaction holds a mode conflicting with it, so it passes queued new requests. A request that is not granted at once joins the queue, conversions ahead of new requests and each of the two in the order the requests were made.

Before it settles for waiting, a request that cannot be granted fells. It takes the transactions holding a conflicting mode on that resource in begin order and fells each one it began before the standing of. The standing of a holder is the earliest begin among the holder itself and every transaction with a request waiting on a resource that holder holds other than the one being asked for. A felled transaction gives up every lock it holds, loses the request it was waiting for and the row request that request was carrying, and takes no further part. The line `wd <asker> <felled>` says so. The request is then tried again. It joins the queue if it still cannot be granted.

Whenever the lock table changes the engine goes back over the resources with a request waiting and looks at the request in front of each, taking the one whose transaction began earliest first. A grant and a felling are both changes, so the pass starts again after either. A request granted this way is granted because no other transaction holds a conflicting mode; it fells nobody.

A grant of a table lock releases the rows of that table that the granted mode covers, and only those. Released rows are free for anyone. Releases print nothing.

A row grant that leaves the transaction holding E or more row locks on that table raises its table lock, once: to the cover of what it holds there with S when every one of those row locks is S, and with X otherwise. The raise is granted only when no other transaction holds a conflicting mode on the table. It never joins the queue and it fells nobody. And a raise that cannot be granted prints nothing and is tried again at the next row grant that leaves the transaction at the limit. A raise that is granted prints `es <transaction> <table> <mode>` and then releases rows exactly as any other table grant does.

A command naming a transaction that is waiting is passed over. So is one naming a transaction that has been felled or has committed.

`gr <transaction> <resource> <mode>` is printed for every grant, carrying the mode the transaction holds once it is done, and `wt <transaction> <resource> <mode>` whenever a request joins the queue. When the script is over, every transaction prints in begin order `tx <transaction> <state> <resource>:<mode> ...`. The state is `run`, `wait`, `cut` for felled or `done` for committed. The resources are in the order that transaction first took a lock on each of them, a conversion leaving a resource where it is and a resource taken again after being released going to the end. Then every resource with a request waiting prints `q <resource> <transaction>:<mode> ...` in queue order, those resources in ascending order with a table ahead of its own rows. Last is `cov <n>` with the number of requests that took no lock. Nothing else is printed.
