`/app` is the feeder of a pretraining run: the half that decides which sample of which source lands in which micro-batch of which rank, and what a run resumed from a checkpoint sees next. A plan is a text file of ops, and `/app/plans` holds four of them. `seed`, `cap` and `src <name> <allowance> <token lengths>` set up the corpus, `mix <names>` is the pattern of sources the stream is dealt from, `open <run> <world> <micro> <accum>` starts a run, `feed <run> <k>` has the feeder produce k more steps and run that far ahead of the trainer, `take <run> <k>` has the trainer consume k steps, producing them first where the feeder has not, `save <run> <mark>` writes a checkpoint, `load <run> <mark> <world> <micro> <accum>` starts a run resuming from one, and `show <run> <step> <rank> <astep>` prints one micro-batch of a step the trainer has completed. `/app/run_feed.py` takes a plan and prints a line for each thing that happens.

The stream is a run of slots numbered from zero. One sample fills each slot. A run takes the stream in steps of `world * micro * accum` slots: step 0 is the slots beginning where the base of that run points, step 1 the slots after those, and a fresh run has base zero. The mix names a source for every slot. Over a stretch of the stream the pattern repeats, and the source of a slot is the entry at the offset of that slot from the first slot of the stretch it lies in. The stream opens as one stretch, at slot zero, with the mix as written. A source hands its samples over one at a time, in the order `/app/feed/shuf.py` gives for that source and the epoch it is in. A sample is delivered into the slot when its token length is at most the cap. One longer than the cap is passed over: it fills no slot, the cursor moves past it, and the same source is asked again, as many times as that takes. A cursor that runs off the end of an epoch goes to the first sample of the next one, under a different order. Nothing is passed over in advance. So where samples above the cap sit at the end of an epoch, a source stands in front of them until it is asked again.

An allowance is a number of epochs. Zero is an allowance that never runs out. A source holding one retires the moment it delivers the last sample that allowance covers, which is the last one inside the cap of the final epoch allowed to it, and after that it delivers nothing. Retiring ends the stretch. The entries of the retired source leave the pattern, the entries that remain keep the order they were written in, and the slot after the one it last delivered into opens a stretch whose offsets are counted from there. Every plan gives at least one source in the mix an allowance of zero, and gives every source at least one sample inside the cap.

Inside a step the slot at offset o goes to rank `o % world`. The slots a rank is given fill its `accum` micro-batches of `micro` samples each in the order they arrive, so the first `micro` of them make up micro-batch 0. `show` prints `show <run> <step> <rank> <astep> <sample> ...` for micro-batch `astep` of that rank, with each sample written as the name of its source, a dot, and the position it holds in the list of token lengths given for that source, counted from zero. A `show` names a step the trainer has already taken.

A checkpoint records what the trainer has completed and what the feeder has produced. Those are not the same number when the feeder has been run ahead. `save` prints `save <mark> <base> <completed> <produced> <source> ...`: the base slot of the run, the steps the trainer has taken, the steps the feeder has made, and then every source in the order the plan declared them. A retired source is written `<name>:gone`. Any other is written `<name>:<epoch>:<cursor>:<delivered>`, which is the epoch being handed over now, how far into the order of that epoch the cursor has reached, and how many samples have been delivered since the plan began. All three count from zero. All three are as the feeder stands before the slot at its own position is filled, and that position is slot `base + produced * world * micro * accum` under the geometry the saved run was using.

A load picks a run up where the trainer left off, not where the feeder had reached. The base of the run it starts is slot `base + completed * world * micro * accum`, reading the base, the completed count and the geometry from that record. It prints `load <run> <base> <source> ...`, holding the state of every source at that slot, written the way `save` writes it. Steps and micro-batches of the new run are counted from that base under the new geometry. A load therefore composes: a checkpoint taken from a resumed run carries the base it was resumed at, and a load of that checkpoint begins there.
