`/app` is the page layer of an ordered index, and it does not behave the way its specification says. Run `python3 /app/run_idx.py <program>` to see what it does now. Four sample programs sit under `/app/progs`. One of them is the size of the large graded ones. Rewrite the five files under `/app/pg` so that every program prints exactly the trace the specification below calls for. Only `/app/pg/fit.py`, `/app/pg/bound.py`, `/app/pg/cut.py`, `/app/pg/join.py` and `/app/pg/step.py` are collected, and they are laid over a fresh copy of the rest of the tree, so changing any other file changes nothing. `/app/pg/step.py` must keep the entry point `one(tr, kind, key, out)`.

A program is a text file whose first non-blank line is `page <capacity> <floor>`, both counts of bytes, followed by one operation per line, either `put <key>` or `del <key>`. A key is 1 to 10 lowercase letters. Graded programs declare a capacity between 32 and 160 and a floor between 10 and one less than the capacity.

The index starts as a single empty leaf page. Leaves hold keys in ascending order. An internal page holds child pages and, between each neighbouring pair of them, one string. Those strings are its entries; a leaf's entries are its keys. Its stored size is 8 bytes, plus 2 bytes for every child it points at. A page that holds at least one entry adds the longest common prefix of its entries once and then 2 bytes and the remaining characters of each entry. A page is over capacity when that size is greater than the declared capacity, and under the floor when it is less than the declared floor.

The string between two neighbouring children is the shortest string that is greater than the greatest key in the subtree on its left and not greater than the least key in the subtree on its right. Every string in the index is that string once an operation has finished. So one whose two keys are no longer the ones it was worked out from is worked out again, and `bound` is printed only when its value actually changes. Within one operation every string that has to be put right is put right before any page is measured against the capacity or the floor.

After the key has gone in or come out, the pages from the leaf up to the root are visited once each, in that order. A page that holds nothing leaves the index; otherwise a page over capacity is cut, and a page under the floor is joined.

An over-capacity page is cut in two. Every position that leaves at least one entry on each side is considered. For a leaf, cutting at position `i` leaves keys 0 to `i-1` behind and moves the rest to a new page. The string promoted to the page above is the one those two neighbouring keys call for. An internal page is cut the other way: position `i` leaves children 0 to `i` behind with the strings before `i`, moves children `i+1` onward to a new page with the strings after `i`, and promotes the string at `i` itself, which leaves this page. A position costs the larger of the two resulting pages plus what the promoted string adds to the stored size of the page above, except that when the page being cut is the root that second part is the whole stored size of the new root, which holds two children and the promoted string. The position of least cost is taken, and the lowest such position when several cost the same. The cut page keeps its id and the other half is a fresh page; when the root is cut, that fresh page is taken before the fresh root. Each page is visited once, so a page that is still over capacity once it has been cut is left as it is.

A page under the floor is joined with a neighbour under the same page above. It takes the one on its right when the joined page would be within capacity, otherwise the one on its left on the same test, otherwise neither. The right page's entries move into the left one, which keeps its id, and the right page is freed. When the two are internal pages, the string that divided them comes down into the survivor, between the children of the one and the children of the other. The root is never joined.

A page that holds nothing, meaning a leaf with no keys or an internal page with no children, leaves the index, and the page above drops it along with one of the two strings beside it: the one on its left when it has a left neighbour, otherwise the one on its right. There is one exception. An empty root leaf stays. Removing a page can leave the page above holding nothing. That page then goes the same way, and only the last removal of such a run puts a string right. While the root is an internal page with a single child, that child becomes the root and the old root is freed.

Sizes are in bytes and ids are whole numbers. A page is given the smallest positive whole number that no page is using; the first page is 1, and a freed id can be given out again. Ids come from the same pool for every kind of page.

Every operation prints its events in the order the work is done, a line each, and nothing else is printed. `add <key> p<id>` names the leaf a key went into and `rm <key> p<id>` the leaf it came out of, while `dup <key>` and `none <key>` say that a put found the key already there or a delete did not find it at all, and in those two cases nothing else happens. `bound p<id> <at> <string>` gives the internal page holding a string that changed, its position there counting from 0, and its new value; `cut p<left> p<right> <at> <string>` gives the page that was cut, the fresh page beside it, the position it was cut at, and the string that went up; `join p<left> p<right>` gives the survivor first and the freed page second. A page leaving the index prints `gone p<id>`. A fresh root over a cut root prints `root p<id>`. A root replaced by its single child prints `fold p<id>`, naming that child. Those are all the events there are.

Every graded program is compared line for line. Two of them are large: about 93000 operations and about 60000 operations, both at a capacity of 96, and the whole graded set has to finish within 120 seconds.
