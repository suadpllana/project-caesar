`/app` holds a small row store we use to rehearse referential changes before they reach the real database. A script is a text file with one item per line. There are four in `/app/scripts`. In a script, `table <name> <col>...` declares a table and its columns, `key <name> <table> <col>...` declares a key, and `ref <name> <table> <col>... -> <key> <mode> <action>` declares a reference from those columns of the table to the named key, paired column for column in the order written. The mode is `simple`, `full` or `partial`. The action is `cascade`, `restrict`, `noaction` or `setnull`. A `setnull` may be followed by the reference columns it clears; with none listed it clears them all. Each `row <table> <id> <value>...` adds a row, `-` meaning null, and after the rows `delete <table> <id>...` deletes those rows of one table as one statement, `dump <table>` prints a table, and `audit` reports on every row. Declarations come first, then rows, then statements. Every name is declared once, before anything uses it.

Everything else under `/app` is put back as shipped before grading, so `run_db.py` will call `drop.delete` and `audit.audit` exactly as it does now, and no package outside the Python standard library can be relied on when it runs.

A reference is inert for a row whose referencing columns are all null, and under `simple` it is inert for a row with any of them null, while under `full` a row with some of them null but not all is broken. Otherwise the row matches every row of the key's table whose key columns equal its non-null referencing columns, so under `partial` a null column matches anything. A row can match itself.

The rows a script gives start with nothing broken, no null in any column of a key, no two rows of a table equal on all of a key's columns, and every reference that is not inert matching at least one row. A delete names only rows that are there. No reference names a key of a table that has two or more `cascade` references.

A delete judges every match on the store as it stood before the delete began: a row loses a reference when it matched at least one row through it and every row it matched is removed, and the delete removes the rows it names and every row that loses a `cascade` reference, and nothing else. So rows that match only one another keep each other. A row that matches itself keeps itself. A row that is not removed but loses a `setnull` reference has that reference's cleared columns set to null, and it counts as cleared even if they were null already. Clearing never changes what is removed. The delete is refused if any row, removed or not, loses a `restrict` reference. It is also refused if, once the removed rows are gone and the clearing is done, a remaining row is broken, holds a null in a column of a key, or matches no remaining row through a reference that is not inert for it, both rows taken with their values after clearing. That end state is the only place `noaction` is checked. A refused delete changes nothing. A delete prints `ok <removed> <cleared>`, counting every row it removed, the named ones included, and every row it cleared, or, when it is refused, `refused <name> <id>`: the failing key or reference declared first in the script, then the smallest id among the rows that fail it. A row fails a `restrict` reference by losing it, and fails any key or reference by breaking one of the end-state conditions above. A `dump` prints `<table> <id> <value>...` for each row of the table in id order, with `-` for null, and prints nothing for an empty table. An `audit` prints `<table> <id> <removed> <cleared> ok`, or the same line ending in `held`, for every row: tables in declaration order, ids ascending within each. The counts and the ending are what `delete <table> <id>` of that one row would print, `held` meaning it would be refused, and the counts are given even then. An audit changes nothing. Nothing else may go to standard output. A run that ends in an error counts as wrong.
