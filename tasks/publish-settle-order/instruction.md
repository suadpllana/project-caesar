`/app` is the extension host we try loader changes on before they go near the shipped one. A program is a text file of ops and `/app/progs` holds a few. A `unit` line declares a unit, `dep` gives it a dependency, and `pre` gives it a unit that has to be up first. Then `pub` is a name the unit publishes and `fall` a name it publishes as a fallback. Its startup calls are the `boot` names. An `auto` line marks a unit as one that a call may bring up. Everything a unit declares is declared before it is first brought up, and no unit names itself. Then `act` brings a unit up, `open` brings it up into a scope of its own, `call` has a unit call a name, and `rel` gives back one hold. That is the whole op set.

`/app/run_host.py` takes a program and prints what happened, a line per event.

We rewrote the loader last cycle and it has been wrong since. Run `/app/run_host.py` on `/app/progs/tiny.txt`. The last line comes out `run u3 s1 u2`. That is wrong. It should name u1, which published `s1` before u2 did, because publishing a name as a fallback does not queue it behind an ordinary publication. The files you may change are `/app/link/walk.py`, `/app/link/view.py`, `/app/link/pick.py`, `/app/link/site.py`, `/app/link/want.py` and `/app/link/drop.py`. Nothing else.

Bringing up a unit that is already up adds a hold to it and leaves its publication exactly where it is. Bringing up one that is not brings up what it names first, dependencies and `pre` units alike, in declaration order, skipping any that is already up or is itself part way up, and then the unit is published at the back of the publication order. Its startup calls run after that, in declaration order, so a startup call sees the order as far as it has been built and no further.

An `act` publishes into no scope. An `open` publishes everything one activation brings up into a single fresh scope, and a call reaches a publication only when that publication is public or sits in the scope the caller reads. A unit reads the scope it came up in. That does not change while it is up. Scopes hold nothing up. They are not units. Naming a unit with `act` while it is up in a scope makes that publication public where it stands, the same publication in the same place in the order, visible to everyone from then on, and the unit itself goes on reading the scope it came up in.

A name is answered by the first unit in publication order that publishes it, is still up, and the caller can see, and a fallback publication competes on that footing and no other.

A call that finds nothing it can see looks for the first unit marked `auto`, in the order the marks were made, that publishes the name and is neither up nor part way up. If none, the call misses. If there is one, the call brings it up as if the caller had named it as a dependency, and everything else follows from that: what comes up is published directly ahead of the caller in the publication order, in the order it comes up and not at the back, it is published into the scope the caller reads, or public if the caller reads none, its startup calls run as they would in any activation, so their events come before the call's own, and the caller keeps it up as a dependency would, for as long as the caller stays up and no longer. It takes no hold. The call is then answered by the rule above over the order as it now stands, which need not be the unit that was brought up, since something that came up ahead of it may publish the name too.

A call from a unit that is not up is not an event. A use is one unit's call of one name. It settles the first time that call is answered, and after that it is never resolved again. While the publication it settled on is still up the call reaches it; once that publication has gone the call is dead and stays dead, and a unit of the same name coming back up, by any route, is not that publication and does not repair it. A call that is not answered settles nothing, so the same call can settle later against a unit that came up, or became visible, in between. A unit coming up has settled nothing, whatever it had settled the last time it was up.

A `rel` gives back one hold from a unit that is up and holds at least one. Anything else it leaves alone. A unit stays up while it holds a hold of its own, while any unit that is still up names it as a dependency, and while any unit that is still up brought it up as the answer to a call. Two units that are up and name each other as dependencies keep each other up, whatever holds are given back. A `pre` decides when its unit comes up and keeps it up no longer than that. Once a hold has been given back, the last unit in publication order that is not staying goes down. Then the question is asked again, since the one that went down may have been all that kept the next one, and that repeats until a pass finds nothing to take down.

Every event is one line, printed when it happens and never sorted. It prints `up <unit>` when a unit is published and `down <unit>` when it goes down. It prints `run <caller> <name> <unit that answered>` for a call that reached one, `miss <caller> <name>` for a call that found nothing, and `dead <caller> <name>` for a call whose publication has gone. That is every event. Nothing else is printed.
