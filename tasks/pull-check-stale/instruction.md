`/app` is a rebuild service. It runs a step when something that step depends on has moved and not otherwise, and it works out what a step depends on by watching what the step does rather than from anything declared up front. A program file describes one workspace and everything that happens to it. `seed <path> <word>` puts a word at a path before the first round. `step <name> <path>` declares a step and the path it writes, and two steps may declare the same path. `op <name> read <path>`, `op <name> look <path>`, `op <name> pull <step>` and `op <name> emit <word>` are that step's script in the order they are written, and `emit` is the last op of every step and the only one. `round` opens a round; inside one, `put <path> <word>` and `cut <path>` are edits made from outside the service and `want <step>` is a request, all taken in the order they are written. `python3 /app/run_eng.py <program>` prints one line for each thing that happens. `/app/progs` holds four programs.

We rewrote this service last cycle and it has been wrong since, in more than one place. `/app/progs/one.txt` is one it still gets right, and it shows what a trace looks like: `round 1`, `run top`, `run base`, `ok top f84232`, then `round 2`, `run top`, `ok top 8875fc`, then `round 3`, `run base`, `run top`, `ok top 8aaa40`, one to a line and nothing else.

The files you may change are `/app/eng/keep.py`, `/app/eng/mark.py`, `/app/eng/hold.py`, `/app/eng/step.py` and `/app/eng/wake.py`. Nothing else. The rest of the tree is replaced by our own copy before a program is run, a new file put beside those five included, so the grammar, the driver and the digest are the ones already there and stay as they are. That copy reaches the five through the names they already carry, so whatever you do inside them has to keep answering to those.

What the service keeps about a step is a record: the observations its last run made, in the order it made them. There are four kinds. A read of a path observes the bytes at that path, or that the path was not there at all. A look at a path observes whether the path is there, and nothing about what is in it. A pull of a step observes the value that step emitted, or that it was dead - never why it was dead, and never that it ran, so a step that runs again and emits what it emitted before leaves the observation standing. The fourth kind belongs to a run that ends with a value: it observes what that run wrote to its own output path, after the writing.

A step is brought up to date like this. A step already on the live chain of pulls is a loop. A step whose record was last found to hold while the workspace was exactly as it is now needs nothing further. Otherwise the record is taken in the order it was made, and the first observation that no longer holds ends the taking; observations after that one are not taken at all. A pull observation is taken by bringing the step it names up to date and then comparing, so taking a record is itself a thing that runs steps.

A record whose observations all still hold leaves the step alone. A record with one that does not means the step runs - unless that step has already run in this round, and then the request ends there and the step is reported stuck instead. A step that has only been taken this round has not run. Every round begins with no step having run in it.

A run takes the ops in order. A read of a path that is there yields the word at it. A read of a path that is not there ends the run: the step is dead with the reason `missing <path>`, and the observation of that absence is the last thing the record keeps. A look yields nothing. A pull brings the step it names up to date and yields that step's value; pulling a step that is dead ends the run, and the step is dead with the reason `via <step>`, naming the step it pulled and not whatever lies under that. Reading a path that some step writes is a read like any other: it observes the bytes standing at that path, and never brings that step up to date. An `emit` ends the run with a value - the word it names, or, when it names `*`, the digest `/app/eng/dig.py` makes of the words the reads yielded and the values the pulls yielded, in the order the run took them. A run that ends with a value writes it to the step's own path; a run that dies writes nothing. A step that is dead stays dead until one of the observations in the record it kept stops holding.

A pull that reaches a step already on the live chain ends the request with that chain: the steps from where that step first stands on the chain through to the one doing the pulling, in order, and then that step again. A run cut short by a loop or by a stuck under it leaves its step as though it had never run - no record, no value, and not counted as having run this round - while a run line already printed stays printed and everything that finished before the cut stands.

These are the lines. `round <n>` as each round opens, counting from one. `run <name>` as a run begins. Then one line for each request: `ok <name> <value>`; or `err <name> missing <path>` or `err <name> via <step>` when the step is dead; or `stuck <name>` naming the step that had already run, which need not be the one the request asked for; or `loop <name> <name> ...` for a chain. Nothing else is printed.

The graded set is thirty-three programs written by hand and three hundred and eight generated ones, and the whole of it has to get through inside 60 seconds. Two of the generated ones are pull graphs twenty-four and twenty-one levels deep in which every level is reachable two ways - seventy-three steps over four rounds and sixty-four over six. Time it. Then call it done.
