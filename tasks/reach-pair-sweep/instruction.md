`/app` is the runtime we try collector changes on before they go near the real one. A program is a text file of ops and `/app/progs` holds a few. `new` allocates an object under an id and may give it a finalizer. `set` stores a reference into a field, `slot` stores one into a named slot of the innermost open frame, and `push` and `pop` open and close a frame. `weak` registers a weak reference under a name, and `pair` puts a key and a value in the pair table. `collect` runs a collection. `runfin` runs whichever finalizer has been queued longest. `/app/run_prog.py` takes a program and prints what happened, a line per event.

The collector behind all that is not written. `/app/cyc/keep.py` holds the entry point `/app/rt/ex.py` calls and nothing else, so every program we run comes back silent. Fill it in. `cycle(h)` is handed the heap and returns three collections: the names of the weak references that collection clears, the ids whose finalizer joins the queue, and the ids it releases. The runtime prints them and sorts each group. So the order you return them in does not matter. `/app/cyc/keep.py` is the only file we will take.

An object survives a collection when it can be reached from the slots of the frames that are open, through the ordinary fields of objects that survive. The pair table is weaker than a field. The value of a pair is reached only while that pair's key is reached, and it makes no difference how that key is being kept.

An object that does not survive, and that was allocated with a finalizer that has not run, is kept anyway. What it reaches is kept with it, and its finalizer joins the queue. It stays kept until that finalizer has run. The first collection after that releases it, unless something live points at it again by then. Which finalizers join the queue is settled from what the collection reached before any of this keeping was granted. A finalizer runs at most once for an object. That holds whatever happens to it afterwards, so one that stores its own object back into a live slot does not earn a second. A weak reference is cleared when its referent cannot be reached from the frames. Being kept so that a finalizer can run is not being reached from the frames. Once cleared it stays cleared, including after the referent is stored back somewhere live.

A collection prints `clr <name>` for each weak reference it cleared, then `fin <id>` for each finalizer it queued, then `rel <id>` for each object it released. Within each of the three, ascending. `runfin` prints `ran <id>`. Nothing else is printed.

`/app/progs/wide.txt` is one of the big ones. About eleven thousand objects, and a pair table written back to front. The ones we grade run several times larger. Whatever you write has to get through the whole set inside 60 seconds, so time it on `wide.txt` before you call it done.

`/app/progs/small.txt` is the short one. It allocates three objects and gives the third a finalizer that stores it into slot `c`. It registers `w1` against the first, puts that first object into slot `a`, and pairs it with the second. Then it collects, runs the queued finalizer, drops slot `a` and collects again. Written correctly, the collector makes it print `fin 3`, `ran 3`, `clr w1`, `rel 1` and `rel 2`, in that order.
