`/app` is the link-keeping half of our row store. It decides what happens to the rows that point at a row being taken out or given a new key. A program is a text file of ops. `/app/progs` holds four of them. A `tab` line declares a table and names its columns, the first of which is its key. A `link` line reads `link <name> <child> <col> <parent> <goes> <moves>`. The rows of `<child>` hold keys of `<parent>` in `<col>`. Its two actions say what becomes of those rows: `<goes>` when a parent row is taken out, one of `drop`, `clear`, `bar` or `wait`; `<moves>` when a parent row is given a new key, one of `follow`, `clear`, `bar` or `wait`. A `put` line adds a row, its values whole numbers, with `-` for an empty column. `out <table> <key>` takes a row out. `mov <table> <key> <key>` gives a row a new key. Those two are the changes, and there are no others. Tables and links come before the first `put`. No table is reachable from itself through the links, and no link empties a key column.

A change works out everything it is going to do against the store as it stood when it began. Only then does it do any of it.

A change carries the row it names. A link acts on the rows of its child table whose column holds the key of a row the change carries. An empty column holds no key and is never one of them. What the link does to them is its `goes` when the change takes a row out and its `moves` when the change gives a row a new key. `drop` takes the row out, and the change carries on from it. `follow` writes the parent row's new key into that column, and where that column is the row's own key the change carries on from that row as well. `clear` empties the column. Nothing carries on from a row that was only cleared. `bar` and `wait` leave the row alone. They are two of the three checks below.

A row's group is the greatest number of links on any chain by which the change reached that row.

A row taken out takes nothing else: a column another link would have written or emptied is left alone. Where two links act on one column of a row, or both take that row out, the one declared first decides.

The lines come out group by group, deepest group first when the change takes a row out and shallowest group first when it gives one a new key. Inside a group they go by table, in the order the tables are declared, then by the key the row had when the change began, then by column. Every line names that same key, whatever the row is keyed by when the line is written. A row taken out prints `drop <table> <key> <link>`. An emptied column prints `clear <table> <key> <column> <link>`. A written column prints `move <table> <key> <column> <value> <link>`. `<link>` is the name of the link that decided it, or `-` for the row the change itself names.

Three things stop a change. A `bar` link stops it when a row of its child table held, in that column, the key of a row this change carries, read from the store as it stood when the change began. That row may well be one this change would itself have taken out. It prints `bar <link> <table> <key>`, naming the first such row by the order the links are declared and then by key. Nothing else is printed and nothing is applied. A key that is already held stops a change that would give a row a key another row of that table holds. It prints `clash <table> <key>`, the smallest such key by table order and then by key. Again nothing is applied. A `bar` is reported ahead of a key that is already held. A `wait` link is answered from the store the change leaves behind. It stops the change when a row that is still there holds, in that column, a key its parent table held when the change began and does not hold now. It prints `wait <link> <table> <key>`, the first such row by the order the links are declared and then by key. The change is then walked back. Rows, emptied columns and moved keys all go back, so that the next change finds the store exactly as this one found it. The lines a stopped change printed before it stopped stand.

A change naming a key its table does not hold prints `none <table> <key>` and does nothing.
