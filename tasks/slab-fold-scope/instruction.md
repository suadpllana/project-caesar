Repair the commit service in /app. A bucket contains slabs of integer keys, and a live key belongs to exactly one slab in its bucket. /app/run_tab.py reads a text program and prints the resulting trace. The editable files are /app/tab/live.py, /app/tab/lay.py, /app/tab/wipe.py, /app/tab/mark.py, /app/tab/take.py and /app/tab/push.py. Only those six files are collected.

`plan p` opens proposal p with a view of the committed store at that moment. The view retains the slab numbers, their complete key sets and when each key arrived. Later changes to the store must not change those retained records. `put p b lo hi`, `cut p b lo hi` and `fold p b lo hi` append parts to p; ranges include both endpoints. `push p` consumes p and runs its parts in order, each against the state left by earlier parts. `bulk p b n lo w g` means plan p, append n puts of width w whose first keys are lo + i*(w+g) for i from 0 through n-1, then push p. Programs use valid commands, unique proposal names, positive widths and nonnegative gaps.

A put moves every key in its range into one new slab. All those keys arrive with this proposal, including keys that were already live. Count as added only the keys that were absent immediately before the put. A cut takes out every currently live key in its range and counts what it actually removed. Empty slabs disappear. Puts and cuts change neither the proposal's retained view nor the committed records saved at push start.

A fold selects the slabs in the proposal's view whose complete retained key sets lie inside its range. A current key belongs to that selection only if both its coordinate and its arrival number match a key in a selected source record. A key put again is a different arrival; a fold preserves arrivals. Examine every current slab containing selected material, including slabs extending outside the named range. A slab containing only selected material is eligible, one containing none is ignored, and one containing both conflicts. Resolve a conflict before applying the minimum-size rule, choosing the smallest slab number if several conflict. With no conflict, fewer than two eligible slabs makes the fold a no-op; otherwise replace all eligible slabs with one new slab carrying exactly their keys and unchanged arrivals. The proposal's own parts do not update its view.

Conflict repair uses the committed slab records saved when this push started, which stay fixed through every retry. In the conflicting bucket, start with every saved head slab sharing a coordinate-and-arrival pair with the conflicting tentative slab. Include every view slab sharing any held key coordinate with an included head slab, and every head slab sharing any held key coordinate with an included view slab, until no further slab qualifies. Arrival numbers do not matter for these additions; gaps between a slab's keys do not count as held keys. Replace the included view records with the included saved head records, preserving all other view records. Replacement removes the entire old record, including keys that have since disappeared.

If that replacement changes the view's slab numbers, key sets or arrivals, discard the whole tentative attempt and run every part again from the saved head with the repaired view. A later conflict can repair another part of the view or another bucket and require another retry. If replacement leaves the view identical, discard the attempt and print `clash p`; this consumes p without advancing the head.

Slabs are numbered globally from 1 in creation order. Discarded attempts return every slab number, and their added and removed counts do not contribute to the result. A successful attempt that created no slab and removed no key prints `void p` and leaves the head unchanged. Every other successful attempt advances the head by one and prints `land p number added removed`. All puts in that attempt carry this new head number as their arrival number. Creating a slab counts even if a later part empties it. Counts are totals across the successful attempt's parts, not the net change in bucket size.

`rows b` prints `rows b count`. `at b k` prints `at b k slab`, using `none` if k is absent. These questions inspect the committed store. The only other output lines are the land, void and clash lines above, in command order. /app/progs contains runnable programs; on /app/progs/tiny.txt the final line must be `land b 2 0 5`, since only five keys in the cut's range were live.
