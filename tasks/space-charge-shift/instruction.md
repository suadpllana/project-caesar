`/app` is the metadata layer of the asset store our workspaces share. The top-level folders are spaces, each with a byte limit, and below them folders hold named entries; an entry is either a folder or a link to an asset. Identical content is kept once and paid for once, so an asset carries a content tag instead of bytes of its own, and a script declares its spaces and its content tags before its first operation. `/app/run_store.py` takes a script and prints one line for every operation in it. `/app/scripts/mixed.txt` and `/app/scripts/wide.txt` are two scripts. The four files under `/app/bil` decide who is charged for what. `own.py` indexes the links, `agg.py` answers a space's usage, `gate.py` decides whether an operation fits the limits, and `edit.py` keeps the accounting up to date. Those four are yours. The store, the operation loop and the checkpoint journal stay as they are.

Run `/app/run_store.py` on `/app/scripts/mixed.txt`. Content `c1` is added at `/main/proj/src/a` and then linked a second time into the archive, the checkpoint `r1` is taken, the first link is removed, and `undo r1` puts it back. Line 11 comes out as `11 use arch=120 main=80`. The right line is `11 use arch=0 main=200`. The rollback gave `/main/proj/src/a` back with the age it always had, which is older than the link in the archive, so the main space is paying for `c1` again. The two lines after it are wrong as well, once for the content asset 2 moves onto and once for the folder that moves out of `main`.

Content with at least one link is charged, whole, to the space holding its oldest link, counting every link of every asset that carries that content. Content nothing links is charged to no space, whatever claims are open. A space's usage is the total size of the content charged to it, and `use` prints one line with every space and its usage, spaces in name order.

A link is given an age when it is created, ages run in creation order, and a link keeps its age wherever it goes: moving the link, or moving any folder above it, changes nothing about it. Ages are never reissued, and neither are asset ids, so an id that has belonged to an asset is refused for a new one even after that asset is gone.

The operations are `mkdir` with a path, `add` with a path, an asset id and a content tag, `link` with a path and the id of an asset that exists, `unlink` with a path, `rmdir` with a path, `move` with a path and the path it is going to, `write` with an asset id and the content tag it takes on, `claim` and `free` with an asset id, `limit` with a space name and a number, `snap` and `undo` with a checkpoint name, and `use`. `rmdir` takes the folder and everything under it in one operation. `move` carries a folder or a single link. No folder moves into itself or below itself. An asset stays in the store while it has a link or a claim is open on it, and goes when its last link is removed with no claim standing, or when the claim is released and it has no links.

An operation is refused when the state it would produce has a space over its limit and higher than that space was before the operation. Lowering a space that is already over its limit is allowed. A limit set below what a space already holds is set, not refused. A refused operation changes nothing at all. That refusal prints `no over`. The rest are `no path` for a path that does not lead where the operation needs it to, `no name` for a name already taken in the folder it would go into, `no id` for an asset id that does not exist or has been used before, `no tag` for content the script never declared, `no loop` for a folder moving below itself, `no held` for claiming what is already claimed or freeing what is not, and `no snap` for a checkpoint name that is not standing. Everything structural is settled before the limit is looked at, in the order that list gives, and an operation that survives all of it prints `ok`.

`snap` records the store under a name. A name already standing is refused. `undo` puts the store back to what that name records: folders, links with the ages they had, assets, the content each asset carries, and the limits. It then drops that checkpoint and every one taken after it. No limit refuses it, and a space it leaves over one stays over. It does not touch claims. An asset created after the checkpoint survives the rollback with no links if a claim is open on it, keeping the content it carries at that moment, and is destroyed if not.

The scripts we grade have the shape of `mixed.txt` and the shape of `wide.txt`. `wide.txt` holds 1500 assets over 1002 contents and moves the folder holding them 1300 times, asking for the usage every second move. The big ones hold 4500 assets over somewhere between 2600 and 3200 contents, and move that folder 4000 times, and six of them are in the set.
