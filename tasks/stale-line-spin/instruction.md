`/app` is the cycle model our kernels team uses to check inter-block synchronization in a GPU kernel launch before it goes near hardware: split-K fixups, grid barriers, look-back scans, tile queues, reductions. The runner `/app/run_launch.py <file>` runs one launch and prints what happened. `/app/launches` holds a few. It has been wrong since we split it up. Run it on `/app/launches/example.txt`. It prints `hang 7`. The right output, given below, has `hang 6`, and that is far from all the model gets wrong.

The files you may change are `/app/sim/line.py`, `/app/sim/mem.py`, `/app/sim/place.py`, `/app/sim/turn.py`, `/app/sim/step.py` and `/app/sim/clock.py`. Nothing else is collected. The rest of `/app` is replaced by a pristine copy before grading, so the parser `/app/sim/load.py`, the printer `/app/sim/say.py` and `/app/run_launch.py` stay as they are. The clock `clock.run(launch)` gets what `load.parse` returns. It must return `(blocks, hang, left, gm)`: the G blocks in number order with the fields `say.py` reads (`n`, `sm`, `at`, `end`, `outs`, and `pc` and `reg` for a block stuck at a spin, `at` staying `None` for a block never placed), the hang cycle or `None`, the number of blocks never placed, and global memory as a dict from address to value. Use Python 3.12 and the standard library only.

A launch file has a `dev S R C` line for S multiprocessors, each holding at most R blocks in slots 0 to R-1 and caching at most C lines, then a `grid G` line that launches blocks 0 to G-1, lines `mem a v` that set word a of global memory to v, with every other word starting at 0, and a `show` line listing the addresses to print at the end. After `prog` comes the program every block runs from its first line, with `name:` lines as labels.

Each block has registers r0 to r7. They start at 0. Values are integers of any size, and nothing wraps. An operand is a register, an integer, or `%bid` (the block number), `%sm` (the multiprocessor it was placed on) or `%nb` (G). An address is `[rN+k]`, `[rN]` or `[k]`, meaning the value of rN plus k. Every instruction reads all its operands before it writes anything. For arithmetic there is `mov rd x`, then `add`, `sub` and `mul rd x y`, then `slt rd x y`, which sets rd to 1 if x < y and to 0 otherwise, and `mod rd x k`, which takes a positive literal k and gives 0 to k-1. Memory is reached through the loads `ld.ca rd [a]` and `ld.cg rd [a]`, the store `st [a] x`, `fence`, and `atom.add rd [a] x`, which adds x to the word in global memory and sets rd to the value it had before; what each does to the caches comes below. A block that issues `work x` at cycle u is busy. It issues nothing more before cycle u+x, or u+1 if x is below 1. Control flow is `bra L`, which always jumps to the label L, with `brz x L` jumping there only when x is 0 and `brnz x L` only when it is not. Finally, `out x` appends x to the values the block prints, and `exit` ends the block. There are no other instructions.

The spins `spin.ca rd [a] c x` and `spin.cg rd [a] c x` make one attempt each time they issue, which is the load that `ld.ca` or `ld.cg` would do, into rd, and the block moves on to the next instruction only if the loaded value c x holds. Here c is `eq`, `ne`, `lt` or `ge`, for equal, not equal, less than and at least, with the loaded value on the left. A failed attempt leaves the block at the spin. A spin never uses rd for its address or for x.

The sums `sum.ca rd [a] n` and `sum.cg rd [a] n`, where n is a positive integer, read n lines, one each time they issue: first the line that holds word a, then the next line up, and so on. Each issue reads its line the way `ld.ca` or `ld.cg` would read a word of it, with the same effect on the cache, and adds the line's four words to a running total. The issue that reads the n-th line writes the total to rd and moves the block on. Until then the block stays at the sum.

Line k of memory is words 4k to 4k+3. Each multiprocessor has its own cache, which starts empty and belongs to the multiprocessor, not to the blocks on it, so blocks arriving and leaving never empty it. Nothing keeps the caches in agreement with global memory or with each other. The cached load `ld.ca` answers from the line if the cache of its multiprocessor holds it. If not, it copies the whole line from global memory as it stands at that moment and answers from the copy, first dropping the held line that was filled earliest if C lines are already held. A hit changes nothing, not even the order lines will be dropped in. The bypassing load `ld.cg` answers from global memory. It drops the line from the cache of its own multiprocessor if it is there. Other caches keep theirs. The store `st` writes global memory and, if the cache of its multiprocessor holds the line, the word in that copy, but it never brings a line in and other caches are left as they were. The atomic `atom.add` works on global memory alone and never reads, fills, updates or drops a cached line. A `fence` empties the cache of its own multiprocessor.

Cycles count from 0. Each cycle has three steps. First, blocks whose work has run out are ready again. Second, while a slot is free and blocks remain, the lowest-numbered block not yet placed goes to the multiprocessor with the most free slots at that moment, ties to the lower number, into its lowest free slot. A slot whose block exited at cycle u is free from cycle u+1. A block placed at cycle t can issue at t. Third, the multiprocessors in number order each issue at most one instruction, from the first ready block in slot order after the slot that issued last on that multiprocessor, wrapping round so that slot comes last. Before the first issue on a multiprocessor, slot 0 comes first. A block is ready when it is placed, has not exited and is not busy. A block at a spin or a sum is ready. The rotation remembers the slot, not the block in it. Every instruction takes full effect before the next one issues, so a store on multiprocessor 0 is seen by multiprocessor 1 in the same cycle.

A launch ends when every block has exited, or when it hangs. It hangs at cycle t when, from t on, every placed block that has not exited sits at a spin with none of them busy, and no attempt at or after t succeeds. A block at a sum does not sit at a spin. The hang is the earliest such t. Every graded launch ends one way or the other.

The output starts with `blk b sm s at t end u` and then the out values of b, for each block that exited, in block order, where s is its multiprocessor, t the cycle it was placed and u the cycle it exited. If the launch hung, `hang t` comes next. Then comes `spin b sm s at t on a` and its out values for each placed block that had not exited, in block order, where a is the address its spin reads. Then `left n` gives the number of blocks never placed. Last, `mem a v` is printed for each shown address, in the order given, from global memory at the end. Nothing else is printed. For `/app/launches/example.txt` the output must be exactly these seven lines, in this order: `blk 0 sm 0 at 0 end 3 0`, `hang 6`, `spin 1 sm 1 at 0 on 5 0`, `spin 2 sm 0 at 4 on 5 0`, `left 1`, `mem 4 2` and `mem 5 0`.
