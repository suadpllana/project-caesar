The tree under `/app` is the part of our inference server that decides what to put on the wire. A request is a recorded list of token ids together with its settings. `/app/reqs` holds a few. `/app/run_stream.py` replays them and prints what the server released. Every step prints one line `<name> em <step> <hex>`, the bytes that left us at that step in hex, with `-` when nothing left, and the last step prints one too. Each request then prints `<name> fi <step> <reason>` exactly once, and the reason is `stop`, `eos` or `length`.

Pieces come from `/app/tok`. Most carry bytes. A few carry none, and characters do not line up with pieces at all, so a wide character can arrive split across two of them, or across one that contributes nothing. A piece that starts a character says how many bytes that character has, and we treat the character as finished once that many have arrived, whatever they turn out to be. One leading space is dropped from a request's output, once, and everything downstream sees the text without it. A request can carry stop strings, a floor and a cap. The floor is the number of tokens we owe the client before we are allowed to end the request. The cap is the most we will ever produce.

Some ground rules, several of which are not what you would do elsewhere.

We never send a byte we would have to take back, and we never sit on a byte that was already safe to send. We grade both halves. Neither half is the safe one. Sending something the request later has to unsay is wrong, and holding something back when nothing could still have changed it is just as wrong, so an implementation that keeps everything until the end scores what one that sends everything immediately scores.

Stop strings are matched against the whole text we have sent the client so far, not against the piece that just arrived, and a piece that carries no bytes contributes nothing to that text, so an occurrence can run straight through one. The floor does not change what we match. It decides one thing only: whether an occurrence we have found is allowed to end the request. Below the floor we keep going, whatever we have found. At the floor and above, the earliest occurrence in the text ends the request, the client's output is everything in front of where that occurrence starts, and the rest goes nowhere. Occurrences are found by where they start, not by where they finish, so a longer stop string that completes later than a shorter one still wins if it starts before it.

An end-of-stream piece below the floor carries no text and the request carries on as if it had not arrived. At the floor or above it ends the request with `eos`. Reaching the cap ends it with `length` instead. We still match at that last step, and a stop occurrence there takes precedence, so the reason is `stop` and the tail is dropped exactly as it would have been anywhere else. A character still missing bytes when a request ends is not sent.

Four things have to keep working and we grade them as hard as the rest. A request with no stop strings releases every complete character the moment it is complete, and a request with a floor and no stop strings is not held back by the floor at all. A request whose stop strings never occur reaches its cap and ends on `length` with everything sent. And a request whose text ends on a live partial that can no longer grow into any stop string releases that text rather than holding it.

The requests we grade are bigger than the ones in your tree. Some run to about forty thousand tokens. The whole graded set has to finish inside nine hundred seconds, so per-step work that grows with how much text the request has already produced will not get there however right its answers are.

We grade the `em` and `fi` lines, in order, exactly, with no partial credit. We grade the requests in `/app/reqs`, a harder set you have not seen, and several hundred generated ones besides, so a rule that happens to fit the requests in front of you will not carry.
